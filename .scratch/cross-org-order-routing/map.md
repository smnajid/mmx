# Cross-organisation order routing (CGD → LOC)

## Destination

A **locked design decision** — topology, consistency model, and how local vs remote routing coexist — written so an OpenSpec change can be proposed from it (`/opsx:propose`). Planning only: **no code**. The way is clear when nothing about *which* architecture is left to decide before someone implements it.

Concrete driver: **CGD** (a TradingClient with no desk, in the new Organisation **CGED**) must route its orders to **LOC** (the TradingHub of Organisation **LODH**) — the first cross-organisation, cross-deployment routing case.

## Notes

- **Domain language**: [CONTEXT.md](../../CONTEXT.md) — esp. *Order routing*, *MMX deployment boundary* (L157–158), *TradingHub*/*TradingClient*, *Routing outcome propagation*, *Global account*, *Delegated institution grant*.
- **Invariant source**: [ADR-0002](../../docs/adr/0002-routed-order-is-two-linked-records.md) — routed order = two linked records, synchronous same-transaction propagation. This effort deliberately **relaxes** that atomicity *across deployments only*; local routing keeps it.
- **Prior hardening**: [.scratch/architecture-deepening/02-routed-outcome-propagation-architecture.md](../architecture-deepening/02-routed-outcome-propagation-architecture.md) — the sync in-process propagation this map must NOT regress for local clients.
- **Every ticket is HITL grilling by default.** Use `/grill-with-docs` (and update CONTEXT.md / propose ADRs inline as terms crystallise). Ask one question at a time.
- **Framing givens (locked while charting — constraints on every ticket, not tickets themselves):**
  1. **Topology = cross-deployment.** CGED and LODH stay two separate MMX instances/DBs talking over the network. No co-location.
  2. **Coexistence = keep both.** Local (same-deployment) routing stays synchronous/atomic and unchanged; remote routing is a new async, eventually-consistent path. Routing is polymorphic (`isLocalHub` vs `isRemoteHub`).
  3. **Connection model = one `connectedHubCode`.** A TradingClient still has exactly one connected hub; that code may now point at a hub in another Organisation. Local vs remote is *derived* (same deployment/org or not). The domain org-guard in `LegalEntity.tradingClient()` must be relaxed accordingly.
  4. **Remote `Routed` timing = after hub accept.** A remote client-side order stays `Received` until LOC confirms the hub-side order exists, then flips `Received → Routed`. `Routed` keeps its meaning: hub-side order exists.

## Decisions so far

<!-- one line per closed ticket -->
- [Transport & protocol for cross-deployment routing](issues/01-transport-protocol.md) — hybrid backbone: **leg A** routing request = synchronous REST handshake (CGD→LOC, immediate accept→`Routed`/reject→`Rejected`); **leg B** outcome return = async via the existing transactional-outbox + **shared-broker Kafka** (LODH-owned, org-suffixed topic, CGED consume-only ACL); LODH inbound handled by a **new dedicated `AcceptRoutedHubOrderUseCase`** (not PM intake) via CGED outbound port `RemoteRoutingGateway`.
- [Routing correlation & idempotency across the trust boundary](issues/04-routing-correlation-idempotency.md) — LODH **trusts** the CGED-minted `RoutingId` (no hub-minted second id); hub-side key = **`(originatingLegalEntityCode, routingId)`** as trust-boundary *containment* (id is already globally unique). Exactly-one enforced by a **partial unique index** on that pair (`WHERE originating_legal_entity_code IS NOT NULL`), **not** the read-check; `AcceptRoutedHubOrderUseCase` turns a unique-violation into an **idempotent success** (returns the existing hub-side accept). Cross-boundary correlation is **`(originatingLegalEntityCode, routingId)` only** — no internal order UUID crosses the boundary (leg B + back-office broadcast key off it).
- [Global-account resolution ownership across deployments](issues/03-global-account-ownership.md) — **CGED resolves, before send.** An external **External Identity** system (CGED-side, new outbound port `ExternalIdentityGateway`) maps `(client, client portfolioNumber, hub) → hub-side portfolioNumber`; the resolved account travels **in the leg-A payload**, LODH never resolves. No remote `GlobalAccountDirectory`; local path keeps its in-process directory (framing #2). Surfaced a **domain correction**: global account is keyed by `(client, client portfolioNumber, hub)`, accounts are multi-currency w/ one reference currency, **currency is not a key** — corrected in CONTEXT; code drift parked out of scope ([09](issues/09-unify-global-account-keying.md)).
- [Remote client reference-data & delegated grants access](issues/02-remote-client-reference-data.md) — **thin client, single authority at LODH.** CGED stores **zero** hub reference data; a remote client reads currencies/rates/grants/counterparties **live from LODH** per request (no replication — leg A is sync, so caching buys no availability), and LODH's **in-process check at leg-A accept is the one true validation**. Delegated grants **mastered on the hub** (keyed by CGD). Seam = **remote-backed existing read ports** chosen by derived local-vs-remote (`HubScopeResolver` unchanged). **Proxy indirection collapses** for remote clients: hub-native institution codes cross the boundary, `"BNP via LOC"` is display-only. Rate-visible UX **preserved, bounded by grant** (grant *is* the exposure control; final veto → 07). **Domain correction (user):** CGD is a **genuine TradingClient of LOC** — *TradingClient is a hub-owned membership that may span organisations* (Organisation owns legal-entity identity; TradingHub owns its client list, which may include foreign-org legal entities); same-org guard relaxes **symmetrically**. Connection is **bidirectional** (CGED holds `connectedHubCode=LOC`; LODH holds CGD in LOC's client list), wired by the registration task.
- [Outcome propagation back to the remote client](issues/05-outcome-propagation-back.md) — **consumer-applied on CGED, eventually consistent, detect-after-fact.** LODH's hub-side propagation is **bypassed for remote pairs** (`originatingLegalEntityCode`'s org ≠ hub's org); the hub tx persists only the hub terminal + the leg-B outbox row and needs **no client address** (Kafka producer-owns-topic inversion; CGED pre-subscribed, filters by `originatingLegalEntityCode`). New CGED use case `ApplyRemoteOrderOutcomeUseCase` (symmetric to 01's `AcceptRoutedHubOrderUseCase`) owns the **idempotent** apply (mirrors ticket 04: already-terminal-in-expected-state → no-op ack; the local `propagate*FromHub` throw-on-already-terminal is unfit for at-least-once). `Routed` is an **acceptable unbounded wait-state**; desync detection out of scope (ops fog). `RoutedOrderPairIntegrityException` **migrates to CGED** (missing-client/mismatched-terminal → DLQ + alert, never silent); **ADR-0002 atomic pair-integrity relaxed to "detect + alert"** across deployments (local = prevent via throw+rollback; remote = detect-after-fact, reconcile out-of-band). Client-side `EXECUTED` **suppression holds** (single source = hub-side event; CGED BO fed by 06's broadcast); handoff to 06 — `clientOrderId` is intra-LODH-only, so CGED BO's client-side `Accounted` callback must correlate by **`routingId`**.
- [Back-office event & contract broadcast across organisations](issues/06-back-office-event-broadcast-cross-org.md) — **nothing changes in MMX.** MMX keeps emitting one hub-side `OrderExecutedV1` + the existing routing-context block; the LOC→CGED contract broadcast is **Deposits back-office-internal** (ADR-0003), targeted via `originatingLegalEntityCode` (globally unique → maps to the target org's back-office instance, no new MMX field), correlated by **`(originatingLegalEntityCode, routingId)`** (inherited from 04). No new MMX event/field/channel; no new inbound MMX callbacks; `Accounted` callback contract unchanged — each MMX instance receives calls only for its own orders (LODH MMX ← hub-side orderId; CGED MMX ← client-side orderId). Cross-org back-office work handed to the Deposits programme (out of scope below).
- [Amendment to 05: leg B carries non-terminal events; silence is never terminal](issues/05-outcome-propagation-back.md#amendment-2026-07-26-leg-b-carries-non-terminal-events-accepted-silence-is-never-terminal) — surfaced by grilling 01's "no stuck-in-`Received`" claim. **Silence is never terminal**: a remote client-side order in `Received` is never auto-terminalized on transport silence; only confirmed LODH signals close it (accept→`Routed`, business reject→`Rejected`, hub cancel→`Cancelled`). **Leg B is the authoritative lifecycle mirror** (amended to carry a non-terminal `ACCEPTED` event, emitted same-tx as hub-side order creation in `AcceptRoutedHubOrderUseCase`); **leg A is the latency fast path** (sub-second `Received → Routed` on the happy path). Bidirectional-partition residual = DR / out-of-band reconciliation, not a state transition. Benign redundancy accepted (leg-B ACCEPTED no-ops when leg A already delivered). Trader-reject rides leg-B `REJECTED` with `origin=TRADER`; routing-failure reject is **HTTP-only** (no leg-B event — no hub-side order created → nothing to mirror; corrected during coherence review to avoid a stale-reject-after-accept race if a grant changes during retry); both persist `origin` (`TRADER` | `ROUTING_FAILURE`) on the client-side order. **ADR-0006 candidate**, deferred per 05's precedent. Ripple: persistent origin is a domain-model change touching the V1 local path (all rejects tagged) + a migration wrinkle (historical routing-failure rejects untagged).
- [Consistency & failure model for remote routing](issues/08-consistency-failure-model.md) — **consolidation ticket; fully resolved.** The end-to-end consistency contract is a populated 8-row failure-edge table (7 edges inherited from 01–06 + the 05 amendment; edge 8 resolved here). **Edge 8 (leg-A transient failure): gateway-owned indefinite retry + backoff + circuit-breaker** via `RemoteRoutingGateway`, transparent to the use case — order stays `Received`, circuit-open emits an ops signal (never a state transition); deterministic routing id (04) makes retry idempotent. **No domain-level periodic desync sweep** — pair-integrity stays event-driven at apply time (05 dec 4); the "leg B never fired" case is covered by three infra signals (consumer lag / broker health / outbox age) = ops fog; catastrophic loss = DR (edge 7). **No new `OrderStatus` value** — `Received` covers all pre-confirmed conditions (in-flight / circuit-open / awaiting-leg-B); retry/circuit/consumer-lag are operational metadata, not domain state. Folds into the **ADR-0006 candidate**.
- [Trust & security boundary between deployments](issues/07-trust-security-boundary.md) — **resolved; four bullets → two decisions + two confirm-and-close.** **Account validation (bullet 3): LODH does NOT revalidate** the CGED-supplied hub-side `portfolioNumber`; the `ExternalIdentityGateway` (CGED-side, per 03) is the authoritative resolver for the cross-org path, trusted by the same principle local routing trusts its own `GlobalAccountDirectory` (no re-check after resolve). Failure shifts to booking time (post-`Executed`, back office/Transactions 2 rejects) → **ops fog** (manual unwind + fix-mapping runbook), not MMX architecture; the `ROUTING_FAILURE` reject origin fires for grant/currency/tenor errors (which LODH validates — it masters the grant) but **not** for account errors. LODH needs **no account-validation port** for the remote path. **Authn identity (bullet 1): transport-proven** — credential binds to one remote legal entity; gateway hands `AcceptRoutedHubOrderUseCase` a proven `originatingLegalEntityCode` (mirrors `X-User-Id` / session scope); leg B already closed by 01 (broker ACL = authz). Credential granularity = per legal entity (V1-moot; belongs to N-client generalization). **Bullets 2 & 4 confirm-and-close:** allow-list = TradingClient membership (02), checked against the proven identity, defense-in-depth (gateway early-reject + use-case domain check); data exposure closed by 02 (grant = exposure control) + 01 (org-suffixed topic, consume-only ACL). **Trust model (symmetric): trust identity, intent, authoritative resolution; validate only what LODH masters.** ADR candidate **ADR-0007** (trust boundary), deferred per precedent.

## Not yet specified

<!-- in-scope fog, not yet sharp enough to ticket -->
- Ops/observability for cross-deployment desyncs (a remote pair stuck half-terminal) — monitoring, alerting, reconciliation. Shape now known per 05: two defined signals — (a) hub-terminal-but-client-`Routed` beyond threshold, (b) pair-integrity DLQ events (missing-client / mismatched-terminal on CGED). Still operational SLO work, not architecture; stays fog.
- Reference-data & config migration to *register* a remote hub connection. Now sharper (per 02): must wire **both** sides — CGED's `connectedHubCode=LOC` pointer **and** CGD's membership in LOC's TradingClient list (in LODH) — plus provision credentials/endpoints. Since CGED stores no hub reference data (02), there is **no reference-data seeding** into CGED; registration is connection + credentials only. Still a `task` ticket, gated on 07's credential/trust decisions.
- Whether/how LODH **validates** the CGED-supplied hub-side `portfolioNumber` (account exists at LOC, belongs to CGD) before booking, vs accepting it as-authored — extends the trust boundary (07). Surfaced by 03.
- Trader/ClientRepresentative UI implications for a remote client (does CGD's settings view change; does LOC's desk show provenance differently).
- Generalising beyond the single CGD→LOC case to N remote clients / N remote hubs.
- **Booking-time account-failure runbook (remote path).** Per 07's "trust the resolver" decision, LODH does not revalidate the CGED-supplied account. A bad mapping surfaces post-`Executed` when the back office / Transactions 2 rejects the contract (order stuck `Executed`, `HandoffStatus` not advancing). Ops runbook needed: manual unwind (reverse the deal) + fix CGED's `ExternalIdentityGateway` mapping. Not MMX architecture.
- **Currency/reference-currency compatibility at booking.** A global account is multi-currency with one reference currency (03). Whether the order currency must match the reference currency (or just be "compatible") is a Transactions-2 / back-office booking rule, not validated by MMX at leg-A. Out of MMX scope; logged so it isn't silently assumed.

## Out of scope

- **Co-locating CGD inside LODH's deployment** — rejected at charting (topology = cross-deployment).
- **Unifying all routing onto one async path** (regressing local PAR→LOC to eventual consistency) — rejected at charting (coexistence = keep both).
- Cross-org routing for ProductTypes other than **Fiduciary** (Deposits remains deferred per CONTEXT).
- V2 hub↔client role flipping.
- **Unifying the local global-account model onto the portfolio key** — surfaced while resolving 03 (currency-keying is factually wrong; corrected in CONTEXT). Fixing it changes local routing (framing #2), so it's a separate future effort, tracked as a defect ([09](issues/09-unify-global-account-keying.md)).
- **The Deposits back-office cross-org broadcast channel** (contract creation/reversal/replace propagation between LODH's and CGED's back-office instances, however the back office is deployed) — ruled out while resolving [06](issues/06-back-office-event-broadcast-cross-org.md): MMX's contract is unchanged (one hub-side `OrderExecutedV1` + routing context; per-order `accounted` callback), so the cross-org broadcast is Deposits-programme work, beyond this map's MMX-focused destination.
