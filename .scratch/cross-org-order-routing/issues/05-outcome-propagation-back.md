## Context from 01 (transport, resolved 2026-07-13)

Mechanism is settled: LODH's existing outbox publishes the outcome to a LODH-owned, org-suffixed Kafka topic; **CGED gets a new inbound Kafka consumer adapter** that applies `EXECUTED`/`CANCELLED`/`REJECTED` to the client-side order. This ticket no longer decides *the channel* — it decides the **application semantics**: eventual-consistency state model, avoiding stuck-non-terminal, how `RoutedOrderPairIntegrityException`/missing-pair translates when the hub can't see the client record, and whether client-side `EXECUTED` still emits no back-office event.

# Outcome propagation back to the remote client

## Question

Today when the hub trader executes/cancels/rejects, MMX **synchronously, same-transaction** sets the linked client-side order (ADR-0002; hardened in the outcome-propagation change). Across deployments this is impossible — LODH cannot write CGED's order table.

Decide the **reverse async path** (LOC → CGD):

- Mechanism: outbox+delivery from LODH → inbound callback/consumer on CGED that applies `EXECUTED` / `CANCELLED` / `REJECTED` to the client-side order, copying `executedRate` / `executionTime` / `dealingReference`, rendering counterparty as `"BNP via LOC"`.
- What replaces the atomic guarantee: the pair is now **eventually** consistent — define the intermediate/terminal states and how a client-side order avoids being stuck non-terminal.
- How the existing `RoutedOrderPairIntegrityException` / missing-pair semantics translate when the pair spans deployments (the hub can't see the client record to assert it exists).
- Does the client-side `EXECUTED` still emit no back-office event (the scoped exception), now that the sides are in different orgs?

## Resolution (2026-07-26)

**The reverse async path is consumer-applied on CGED, eventually consistent, and detect-after-fact.** The hub-side synchronous propagation is **bypassed for remote pairs**; CGED's new `ApplyRemoteOrderOutcomeUseCase` owns the apply, idempotency, and broken-pair detection. **ADR-0002's atomic pair-integrity is explicitly relaxed to "detect + alert" across the boundary** — the mirror of how this effort relaxes atomic execute (framing #2). Grilling locked five decisions:

**1. Hub-side propagation bypassed for remote pairs; the hub needs no client address.** LODH's `RoutedOrderOutcomePropagation` port (today: `requireClientOrder` → `findRoutedClientOrderByRoutingId` in the same DB → throw `RoutedOrderPairIntegrityException` on missing, `RoutedOrderOutcomePropagationService.java:69-80`) does **not** run for a remote pair — LODH cannot see CGED's order table, so running it would throw spuriously on every remote terminal. For a remote pair the hub execute/cancel/reject transaction only persists the **hub-side** terminal transition and schedules the leg-B outbox row; it never looks up the client. "Remote pair" = *`originatingLegalEntityCode`'s Organisation ≠ this hub's Organisation* (the hub-side read of framing #2's `isLocalHub`/`isRemoteHub`). Local pairs keep the existing in-process atomic propagation unchanged (framing #2 coexistence).

LODH needs **no knowledge of the client deployment's address** — the load-bearing reason ticket 01 chose the shared broker over point-to-point HTTPS. LODH publishes to its own org-suffixed topic `mmx.routed-order-outcome.LODH`; addressing **inverts** — CGED's consumer is pre-subscribed (consume-only ACL, wired at connection-registration) and filters `originatingLegalEntityCode ∈ {its own LEs}` (== CGD) before applying by `(originatingLegalEntityCode, routingId)` (ticket 04's key). The producer is blind to who is listening; the model generalises to N remote clients on one topic.

**2. `Routed` is an acceptable unbounded wait-state by contract.** A remote client-side order's lifecycle is `Received → Routed` (leg-A accept, framing #4) → unbounded wait → `Executed`/`Cancelled`/`Rejected` (when the leg-B event lands). The client PM sees "awaiting hub" exactly as local `Routed` implies today. Desync detection (transient/persistent leg-B delivery failure — consumer down, broker outage, outbox relay stalled) is **out of scope** for this design decision and stays in the map's *Ops/observability* fog as operational SLO work, not architecture.

**3. The CGED apply is idempotent — mirroring ticket 04.** Leg B is at-least-once Kafka; duplicates will arrive. Today's `propagate*FromHub` → `status.transitionTo(...)` throws on already-terminal (`OrderStatus.java:30-33`: `EXECUTED → {ACCOUNTED}` only; `CANCELLED`/`REJECTED` hard terminals) — correct for in-process local propagation (called once per hub transition), but a poison-message trap under at-least-once: a redelivered outcome on an already-terminal client order throws → retry loop → DLQ, manufacturing a false alarm (or worse, sticking the client `Routed` if the first apply crashed before the offset commit). The CGED consumer mirrors ticket 04's philosophy: a client order already in the event's **expected** terminal state → **no-op ack** (offset advances); only a **mismatched** terminal (a different outcome for the same pair — unreachable, since the hub transition is itself once-only) is an error.

This lives in a **new CGED use case `ApplyRemoteOrderOutcomeUseCase`** — the symmetric counterpart to ticket 01's `AcceptRoutedHubOrderUseCase` (leg-A inbound seam on LODH; this is leg-B inbound seam on CGED). It owns load-by-`(originatingLegalEntityCode=self, routingId)`, the idempotency check, broken-pair handling (decision 4), and the apply; the Kafka consumer adapter is a thin decode-and-call shell. The existing `RoutedOrderOutcomePropagationService` is **not reused** — it is hub-side with a throw-on-missing contract and a deliberate throw-on-already-terminal that local propagation depends on; forcing remote semantics into it would change local behaviour.

**4. `RoutedOrderPairIntegrityException` migrates to CGED; the invariant's power changes across the boundary.** With the hub-side propagation bypassed (decision 1), the hub-side throw no longer fires for remote pairs — it is *local-pairs-only*. The invariant moves to where the client record lives: CGED's `ApplyRemoteOrderOutcomeUseCase`. Missing client, or mismatched terminal → throw the **same** `RoutedOrderPairIntegrityException` (one exception names one invariant; the caller decides handling) → consumer catches → **DLQ + ops alert**, never a silent ack (the exact desync the architecture-deepening change removed). Note what "missing client" means here: routingId is deterministically minted from the client order id (ticket 04) and CGED only processes events for its own `originatingLegalEntityCode`, so a missing client is not "lost same-DB record" (the local meaning) but **"LODH asserting an outcome for a CGD order CGED never placed"** — corruption, or a trust-boundary violation on ticket 07's allow-list axis.

**Load-bearing asymmetry (document this):** locally the throw fires *inside the hub's execute tx* and **rolls back the hub terminal** (broken pair → hub never reaches EXECUTED); remotely that is impossible — LODH is already terminal before CGED sees the event, and CGED cannot unwind LODH's tx. So the remote broken-pair is **detected after the fact, not prevented**: LODH stays terminal, the client cannot be mirrored, reconciliation is an ops act. **ADR-0002's atomic pair-integrity is relaxed to "detect + alert" across deployments** — the mirror of how this effort relaxes atomic execute.

**5. The client-side `EXECUTED` back-office suppression holds cross-org — single source stays the hub.** CONTEXT L130's scoped exception is unchanged: CGED's `ApplyRemoteOrderOutcomeUseCase` does **not** schedule a back-office outbox row for the client-side EXECUTED. The sole emitter remains LODH's hub-side `ExecuteOrderService` (one `OrderExecutedV1` with routing context; `ExecuteOrderService.java:87`). `suppressesExecutionHandoff()` = `isRoutedClientSide() && status == EXECUTED` already evaluates true for a remote client-side order (`routingId` set, `originatingLegalEntityCode` null) — the domain rule covers remote without edit. Rationale: preserves the one-event-per-routed-trade invariant; consistent with ticket 02's thin-client/hub-is-master symmetry (CGED's BO *receives* a contract via broadcast, it does not *originate* one). **Condition: ticket 06 delivers the cross-org LOC→CGED back-office broadcast.**

**Handoff / inherited by:**
- **Ticket 06** (cross-org back-office broadcast): the hub-side event's `ExecutionHandoffRoutingContext.clientOrderId` (UUID) is henceforth an **intra-LODH** construct (ticket 04: no internal order UUID crosses the boundary). The cross-org broadcast carries `(originatingLegalEntityCode, routingId)` + booking facts only. Consequence: when CGED's BO later calls CGED's MMX `accounted` callback for the client-side order (CONTEXT L127, the independent client-side `Accounted`), it **cannot correlate by `clientOrderId`** — it must correlate by **`routingId`**. CGED's MMX needs a routingId-keyed `accounted` path (or CGED's BO resolves the orderId via a routingId lookup before calling back). 06 owns this correlation decision.
- **Ops/observability fog** (map): sharpened by 05 — desync now has two defined ops signals: (a) hub-terminal-but-client-`Routed` beyond threshold (decision 2's detection), (b) pair-integrity DLQ events (decision 4). Still operational SLO work, not architecture; stays in fog.

**Spec/doc note (planning-only, consistent with 01/04):** no CONTEXT.md edit and no new ADR now. "Routing outcome propagation" (CONTEXT L123-124) already describes the synchronous same-transaction model; the cross-org async relaxation is *unbuilt*, and documenting it as fact would violate the planning-only stance (ticket 04's precedent: avoid documenting unbuilt behaviour). The ADR-0002 relaxation (decision 4) is load-bearing and ADR-worthy by the domain-modeling test (hard-to-undo architecture relaxation, surprising without context, real trade-off vs distributed-tx/2PC) — but, per the architecture-deepening decision #8 pattern and this map's destination, it is captured here and will be encoded in the OpenSpec change's `design.md` when `/opsx:propose` runs; elevation to **ADR-0005** is deferred to when that change lands (or if still load-bearing after implementation).

## Amendment (2026-07-26): leg B carries non-terminal events (ACCEPTED); silence is never terminal

**Origin.** Surfaced by grilling ticket 01's "no stuck-in-`Received`" claim. 05 scoped leg B to terminal outcomes and declared `Routed` an acceptable unbounded wait-state (decision 2). That left `Received` — not just `Routed` — with an unbounded-wait case: if leg A's synchronous response is lost (timeout, partition, CGED crash before recording), the client-side order cannot reach `Routed` via leg A alone, and 05's terminal-only leg B cannot close `Received → Routed` (a non-terminal transition).

**Locked decision (this grill): silence is never terminal.** A remote client-side order in `Received` is never auto-terminalized on transport silence. The only closers are (a) a confirmed accept signal → `Routed`, (b) a confirmed business reject → `Rejected`, (c) a confirmed hub cancel → `Cancelled` — each requiring a real signal from LODH. Transport silence stays `Received`; the bidirectional-partition residual is a DR / out-of-band reconciliation concern, not an order-lifecycle state transition. `Received`'s unbounded-wait contract mirrors 05 decision 2's treatment of `Routed`.

**Consequence (load-bearing): leg B is the authoritative lifecycle mirror; leg A is the latency fast path.** For "silence is never terminal" to hold without indefinite `Received` on the common case (leg-A response lost, LODH healthy), leg B must close `Received → Routed` itself. 05's terminal-only vocabulary cannot. Therefore leg B is amended to carry the non-terminal ACCEPTED event.

**Minimal amendment:**
1. **New event type `ACCEPTED`** on the existing LODH-owned topic `mmx.routed-order-outcome.LODH` (no new topic; type discriminator in payload). Emitted from `AcceptRoutedHubOrderUseCase`'s transaction — outbox row committed in the same tx as hub-side order creation, so the accept signal is *exactly as durable as the hub-side order* (if the order exists, the row exists).
2. **Payload:** `(originatingLegalEntityCode, routingId, acceptedAt)` — minimal; `markRouted(routingId, now)` requires only these.
3. **Consumer:** `ApplyRemoteOrderOutcomeUseCase` (decision 3) extended to handle ACCEPTED idempotently — `Received → markRouted`; already-`Routed` (leg A delivered first) → no-op ack. Extends decision 3's already-terminal no-op philosophy to the non-terminal case; same idempotency key `(originatingLegalEntityCode, routingId)` (ticket 04).
4. **Benign redundancy:** when leg A delivered accept (the common case), the leg-B ACCEPTED event arrives and no-ops. The deliberate price of leg B being authoritative rather than advisory; acceptable at money-market order volume.

**Decision 5 (client-side EXECUTED back-office suppression) holds unchanged** — ACCEPTED is non-terminal and triggers no back-office emit; only the hub-side EXECUTED emits (one event per routed trade).

**Resolved (2026-07-26): REJECTED is unified; origin is a persisted field.** The ubiquitous-language sharpening of `Rejected` (CONTEXT) names *origin* as the PM-facing distinction, so origin is first-class: a **`origin`** field (values `TRADER` | `ROUTING_FAILURE`) is **persisted on the client-side order's rejection record**, so the distinction is queryable/auditable, not just present at apply time.

**Corrected (2026-07-26, coherence review of 01–08): routing-failure reject does NOT ride leg B.** The original resolution placed LODH's routing-failure reject on leg B under `REJECTED` with `origin=ROUTING_FAILURE`. Re-reading against this amendment's own principle — *"leg B is the authoritative lifecycle **mirror**"* — surfaced a defect: a routing-failure reject creates **no hub-side order** (intake refused it, CONTEXT L112), so there is no lifecycle for leg B to mirror. Emitting a leg-B `REJECTED` for a no-order-created reject creates a race: if the leg-A HTTP reject response is lost and the grant later changes (prospective grant lifecycle), a retry accepts and emits leg-B `ACCEPTED`; the stale `REJECTED` then wrongly terminalizes the now-valid order. Resolution: **a routing-failure reject is HTTP-only** (no leg-B outbox row). The client-side order becomes `Rejected` (origin=`ROUTING_FAILURE`) when CGED receives the HTTP reject response; if that response is lost, the gateway retries (edge 8) or the order stays `Received` (edge 7 / DR) — consistent with "silence is never terminal" (a lost reject is silence, not a terminalization). **Leg B's sole `REJECTED` is the trader-reject** (origin=`TRADER`) — *always* a hub-side order transitioning to terminal, which leg B genuinely mirrors. `ApplyRemoteOrderOutcomeUseCase` applies trader-reject `→ Rejected` from `Routed` (the order is `Routed` when the desk rejects) and persists the origin.

The origin field is still set for routing-failure rejects — just not via leg B: edge 1 (CGED-side unresolved account) sets it directly at CGED intake; edge 2 (LODH intake routing-failure) sets it when CGED receives the HTTP reject response. Both persist origin=`ROUTING_FAILURE` on the client-side order.

**Ripple (scope note — persistent origin is a domain-model change touching the local V1 path, not only cross-org):** a persisted `rejectionOrigin` on `MoneyMarketOrder` tags *all* rejections — V1 local (trader-reject via `reject()`, routing-failure at intake per CONTEXT L112) as well as cross-org. Every method that sets `rejectionReason` (`reject`, `propagateRejectFromHub`, and the intake routing-failure path) gains the origin. Migration wrinkle: V1 *already* persisted routing-failure rejects (intake rejects with a reason) without an origin tag — historical rows cannot be cleanly reclassified from reason text alone, so backfill is either `UNKNOWN`/null for pre-amendment rejects or a heuristic on reason text. Migration strategy is implementation-scope (OpenSpec change tasks), not architecture; flagged here so the change proposal doesn't treat "add origin field" as a one-line edit.

**ADR candidacy.** "Silence is never terminal + leg B authoritative lifecycle mirror" is ADR-worthy by the domain-modeling test (hard-to-reverse: shapes the whole failure model; surprising without context: "why can a remote `Received` sit forever during a partition?"; real trade-off vs auto-reject-on-timeout / reverse-reconciliation). Per 05's own precedent (capture now, elevate when the change lands), it is captured here and will become **ADR-0006** in the OpenSpec change's `design.md`. Not written to `docs/adr/` yet.
